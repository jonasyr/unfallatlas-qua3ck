## Overview

This document describes the use of AI-based tools within the context of this project with machine learning algorithms. The outline follows the QUA3CK process model to illustrate which tools were used for what purpose at each phase of the project.

The QUA3CK model is an iterative process for developing ML solutions. It stands for:
- **Q**: Question
- **U**: Understanding
- **A3**: **A**lgorithm Selection, Data **A**daptation, Parameter **A**djustment
- **C**: Conclusion & Comparison
- **K**: Knowledge Transfer

> All results generated by AI systems (e.g., code, analyses, etc.) were critically reviewed, validated and adapted by me as the responsible developer. I bear full responsibility for the project.

## Tooling infrastructure used throughout

Beyond the AI models listed per phase below, every Codex and Claude Code session on this project ran with the following tooling attached. These are not one-off, phase-specific uses. They were active in essentially every session and materially shaped how the AI tool worked, including what it could see, how precisely it could edit, and how it turned a request into a plan before touching any file. They are disclosed here once rather than repeated per row.

- **[Serena MCP](https://github.com/oraios/serena)** is a semantic, symbol-aware code-navigation and editing server. Instead of dumping whole files into context, it lets the AI look up a function or class by name, read only the symbol it needs, and edit at the symbol level. I use it because it keeps edits precise and scoped, which reduces the risk of silently rewriting unrelated code. It also keeps context usage low enough to work across this repository's larger notebooks and modules without truncation.
- **[Codebase Memory MCP](https://github.com/DeusData/codebase-memory-mcp)** provides a graph-indexed memory of the repository, including call graphs, data flow, and architecture. The AI can query it instead of re-deriving structure from scratch every session. I use it so the AI can trace how a change in one module, such as `src/unfallatlas/features/preprocessing.py`, propagates to the notebooks that import it instead of guessing from file names.
- **[Superpowers Plugin](https://github.com/obra/superpowers)** provides structured workflow skills such as `brainstorming`, `writing-plans`, `executing-plans`, and `systematic-debugging`. These skills govern how a request becomes work. The workflow clarifies and designs first, creates an explicit and reviewable implementation plan second, and executes task by task third. I use it to keep larger builds, such as the full C-phase notebook, from becoming one large unreviewed AI-authored change. Every non-trivial build in this project has a corresponding design specification or implementation plan under `docs/superpowers/` as a paper trail.

None of these tools generate project content on their own. They change how the underlying AI model, Claude or Codex as listed per row below, reads and edits this specific repository. Their effect on the result is material. They influence which files get read, how narrowly an edit is scoped, and whether a build proceeds through an upfront plan or an ad hoc approach, even though the tools themselves never appear as an "AI tool" row in the table below.
